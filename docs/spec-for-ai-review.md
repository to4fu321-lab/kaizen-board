# カイゼンボード（KAIZEN BOARD）仕様書 v2

> 個人制作のポートフォリオ用プロトタイプ。特定企業の実際の業務システムではなく、
> ロゴ等も使用していない非公式のデモアプリ。データは端末内（ブラウザのlocalStorage/IndexedDB）
> にのみ保存され、外部には送信されない。

---

## 1. コンセプト

物流センター・倉庫の現場で働くスタッフが、日々感じる「ちょっと困った」「危ない」「こうしたい」を
30秒で報告でき、それが実際の改善につながるところまでを一気通貫で扱う業務改善ツール。

「採用担当者に見せるためのアプリ」ではなく「現場で働く人が本当に毎日使いたくなる改善ツール」を
目指して設計している。次の循環が成立することを最重要方針としている。

```
気づく → 報告する → 共有する（共感が集まる） → 管理者が判断する
       → 対応する → 改善する → 効果を確認する → 良い改善を他拠点に広げる
```

舞台は「札幌物流センター」（デモ用の架空拠点）。横展開の相手として「船橋物流センター」
「大阪物流センター」の2拠点が登場する。

---

## 2. ユーザーとロール

| ロール | 立場 | できること |
|---|---|---|
| 現場スタッフ | 気づく人・報告する人 | 報告の投稿／編集／取り消し、共感リアクション、自分の実績確認 |
| 管理者 | 判断する人・改善を進める人 | 自拠点の報告への対応、横展開、他拠点事例の閲覧 |

画面上部の「現場／管理者」切り替えでロールを行き来できる（デモ用の簡易実装）。

## 3. 情報設計・データモデル

### 報告（Report）
| フィールド | 内容 |
|---|---|
| カテゴリ | 安全 🦺／作業効率 ⚡／品質 🎯／設備 🔧／整理整頓 📦／在庫 📋／その他 🙋 の7種 |
| 緊急度 | 危険／早めに／通常の3段階。カード左端の色帯で表現（危険=赤、早めに=アンバー、通常=非表示） |
| タイトル・本文 | 40字以内のタイトル＋任意の詳細文 |
| 元メモ（rawNote） | AIで文章を整えた場合、現場が書いた元の箇条書きを別途保持（後述） |
| 場所 | 拠点内のエリア（ピッキングエリア／入荷バース等）＋自由記述の補足メモ |
| 画像 | Before（現状）／After（こうしたい）の2枚まで。手書き注釈つき |
| ステータス | 下記「4. 改善プロセス」参照 |
| 横展開フラグ | 全拠点へ横展開／本社へ報告、の2種類（独立したフラグ、対応ステータスとは別軸） |
| リアクション | 共感（like）／自分も困ってる（same）の2種、人数を表示 |
| 対応履歴（actions） | すべてのアクションを時系列で保持。コメント・加算ポイント・日時つき |

### ユーザー（User）
氏名・役割（staff/admin）・所属拠点・チーム名（＝業務区分）・アバター色。

### お知らせ（Notice）
管理者から現場への連絡。種類（ルール変更／他拠点の改善／今月のまとめ／お知らせ）、
タイトル・本文、発信元拠点、宛先（全員／業務区分／個人の3通り）、確認した人の一覧、
関連する報告への参照を持つ。

## 4. 改善プロセス（ステータス設計）

```
未対応 → 確認中 → 採用／一部採用 → 対応中 → 完了
                 ↘ 見送り（理由必須）
```

- **未対応**：投稿された直後
- **確認中**：管理者が受け取ったことを伝えた状態
- **採用／一部採用**：実施が決定した状態（採用は+50pt、一部修正しての採用は+30pt）
- **対応中**：実施に着手した状態
- **完了**：改善が実際に終わり、現場がどう変わったかのコメントが記録された状態（+20pt）
- **見送り**：今回は対応しない（コスト／安全面／優先順位／他部署調整／設備制約／現時点では対応不要／その他、から理由を選択。見送り＝悪ではなく「何を今はやらないかの判断」として扱う）

管理者の対応画面では、**今のステータスから次に選べるアクションだけ**を表示する
（例：採用済みの案件には「対応中にする」「完了にする」だけが出る）。これにより管理者が
毎回全選択肢から迷わずに済む。

「完了にする」を選ぶと、改善後どう変わったか（例：「探す時間が減った」「通路が広くなった」）の
記入が必須になり、報告詳細画面に**「改善のあゆみ」＝改善前 → 実施した改善 → 改善後**の
3段ストーリーとして表示される。「報告して終わり」にしないための中核機能。

## 5. 主な機能

### 5.1 現場スタッフ側（スマホ、片手操作前提）

- **3ステップの投稿フロー**：①カテゴリ・緊急度 → ②写真（任意） → ③タイトル・本文・場所
- **写真への手書き注釈**（Canvas自作）：ペン／矢印／丸／**文字入力**の4ツール、色4種・太さ2種、1つ戻す・全消し。文字ツールはタップした位置にテキスト入力欄が出て、確定すると黒縁取り付きの文字が写真に描き込まれる
- **音声入力**：タイトル・本文欄にマイクボタン。Web Speech API対応ブラウザでは、しゃべった内容がそのまま入力される（非対応ブラウザではボタン非表示、既存入力を妨げない）
- **AI文章サポート「整える」**：箇条書きのメモを、Claude API（`claude-opus-5`）でタイトル・本文の報告文案に変換。書くのが苦手な人・外国籍スタッフが「うまく書けないから報告しない」を防ぐ設計。
  - 結果は必ず見比べてから「これにする／元のまま」で選択（自動置換しない）
  - 使わずにそのまま投稿することも可能（完全に任意）
  - 元の箇条書き（rawNote）は必ず保存され、管理者は対応画面から「現場が書いた元のメモを見る」でいつでも閲覧できる
  - プロンプト側で「書かれていないことを足さない（原因推測・対策提案・誇張の禁止）」「現場の固有の言い方（3号台車、A-1通路等）を残す」を明示
  - サーバー側API（`/api/polish`）でのみAPIキーを使用、ブラウザには一切渡らない
- **Before/After比較スライダー**：ドラッグで見比べ（指・マウス・キーボード対応）
- **投稿の修正・取り消し**：自分の投稿のみ、いつでも編集・削除可能。画像は変更しなければ元の参照を維持
- **拠点をまたぐ事例共有**：自分の拠点の報告に加え、他拠点で「横展開」された事例がフィードに流れてくる（🏢マーク付き）
- **共感リアクション**：「共感する」「自分も困ってる」の2種。「n人が同じ課題を感じています」という管理者向けの判断材料として機能（SNS的な人気ランキングにはしない）
- **ポイント・レベル・バッジ**：投稿すること自体に+10pt（採用可否に関わらず）。レベルは「カイゼン見習い→アシスタント→リーダー→マイスター→レジェンド改善家」の5段階。バッジは「はじめの一歩」「安全の報告をした」「現場が変わった」等7種、投稿履歴から都度導出（保存しない）
- **マイページ**：報告した／採用された／改善された、の3つの貢献実績＋バッジ＋今月のランキング（トップ3＋自分の順位）。ゲームのレベル上げでなく「自分がどれだけ改善に参加したか」の振り返りとして設計
- **初回だけの導入画面**：「現場の『ちょっと困った』を、カイゼンに変える。」→気づく→報告する→共有する→改善する、の4ステップを一度だけ表示（localStorageで既読管理）
- **PWA対応**：ホーム画面に追加してアプリとして全画面起動、オフラインでも開ける（Service Worker）

### 5.2 管理者側（PC/タブレット想定）

- **開いた瞬間が「未対応」から始まる**：全件表示ではなく、今すぐ手を打つべき案件から
- **自拠点の案件のみ表示**：他拠点の案件は混在させず、「🏢 他拠点」タブに分離（横展開された事例を参考として閲覧するのみ、対応操作はできない）
- **並び順は緊急度が最優先**：危険→早めに→お待たせしている順（同緊急度は古い順）
- **危険な未対応は最上部に警告ブロック**として常時表示
- **ダッシュボードの数字**：未対応件数（最重要、大きく表示）／危険件数／今月の報告件数／採用率。KPIを増やしすぎず、現場の判断に直結する数字だけに絞った
- **フィルタは3分類**：未対応／対応中／完了（対応中には確認中・採用・一部採用・対応中の全ステータスを含む、完了には完了・見送りを含む）
- **対応アクション**：確認中にする／採用する(+50pt)／一部修正して採用(+30pt)／対応中にする／完了にする(+20pt、改善後コメント必須)／お礼を送る(+5pt)／見送る（理由選択式）。**今のステータスから選べるものだけ**を表示
- **横展開**：「他拠点へ横展開する」(+20pt)／「本社へ報告する」(+10pt)の2つ、対応ステータスとは独立したトグル。もう一度押すと解除（ポイントも自動で戻る）
- **改善のあゆみ**：報告詳細と同じ3段ストーリー表示で、対応中の案件がどこまで進んでいるか一目で分かる

### 5.3 管理者から現場への連絡（お知らせ）

報告は「現場 → 管理者」の一方向なので、逆向きの連絡手段を持たせた。3ステップの1画面で完結する。

- **連絡の種類は4つだけ**：📋ルール変更／🏢他拠点の改善／📊今月のまとめ／📣お知らせ
- **宛先は3通りだけ**：全員／業務区分（班）／個人。選ぶと「◯◯班へ 2人に届きます」と送信前に必ず出る
- **AIによる今月のまとめ**：報告件数・採用件数・完了件数・危険件数・横展開件数・カテゴリ内訳を
  **アプリ側が集計**し、その数字だけを渡してAIが文章化する。AIに数えさせない設計にしてあり、
  送信画面には「アプリが数えた数字です」として集計値そのものを並べて表示する
- **他拠点の改善事例の紹介**：他拠点から横展開された事例を選ぶと、「現場からの報告」と
  「対応の経過（管理者コメント）」がそのまま材料として表示される。「これから取り入れます」
  ではなく、「よそでこんな改善があり、こう良くなった」という事例紹介として下書きが入る
- **AIが無くても完結する**：種類や事例を選んだ時点で数字・事例入りの下書きが入るので、
  APIキー未設定でもそのまま送れる。AIボタンは「読みやすく整える」上乗せの位置づけ
- **既読は押してもらう**：現場側は各お知らせの「確認しました」ボタンで既読にする。
  管理者側の一覧に「確認 2/3人」と出るため、ルール変更が伝わったかを確認できる
- 現場側はフィード上部の帯と、下部ナビの未読バッジの2箇所から気づける

## 6. デザイン方針

- 配色は **オレンジ（ブランド・主要アクション専用）／白／明るいグレー／濃いネイビー**を基調。TRUSCO・オレンジブック・物流・工具・現場を想起させつつ、オレンジは画面全体に多用せず「進めるアクション」に限定
- 色の役割を固定：オレンジ=ブランド／主要アクション、赤=危険・緊急のみ、個別のステータス色（アンバー/緑/青緑/青）=進行状態、グレー=補足・非アクティブ
- 文字サイズは4段階のみ（タイトル20px／見出し16px／本文14px／補助12px、数字表示のみ28pxの例外）。情報量を増やすより「必要な情報が一瞬で分かる」ことを優先
- ステータスは基本、丸ドット＋グレー文字で控えめに。ただし「採用」「完了」だけは朱色の**ハンコ風スタンプ**（二重枠・傾き・ポップアニメ）で例外的に強調し、「押した」達成感を演出
- 避けたもの：SNSっぽさ、ゲームっぽさ、過剰なグラデーション・角丸・アニメーション、情報の詰め込み、採用資料のような演出

## 7. 技術構成

- **フレームワーク**：Next.js 16（App Router）／React 19／TypeScript／Tailwind CSS v4
- **状態管理**：`useSyncExternalStore`を使った自作の単一ストア。データはlocalStorage（報告メタデータ）＋IndexedDB（画像Blob）に永続化。バックエンドは存在せず、すべて端末内で完結（AI機能を除く）
- **AI機能**：Next.js API Route（`/api/polish`）から`@anthropic-ai/sdk`でClaude API（`claude-opus-5`）を呼び出し。構造化出力（Zod）でタイトル・本文を受け取る。APIキーはサーバー環境変数のみで保持
- **画像処理**：Canvas APIで手書き注釈を自作実装（ライブラリ不使用）
- **PWA**：`manifest.ts`＋`public/sw.js`（Service Worker、network-first/cache-first戦略）
- **ホスティング**：Vercel

## 8. 評価してほしい観点（例）

- 「報告して終わり」にしない改善サイクルの設計として、抜けている段階やUXの矛盾はないか
- AI文章サポート（箇条書き→報告文）の設計は、原文保持・任意性・非改ざんの3条件で十分に安全か
- 管理者ダッシュボードの情報量・優先順位づけは、実際の現場運用で機能しそうか
- ステータス設計（未対応→確認中→採用→対応中→完了、見送りの分岐）に無理はないか
- ポイント・バッジ制度が「ゲーム化しすぎ」になっていないか、または逆に動機づけとして弱すぎないか
- 「現場スタッフが本当に毎日使いたくなるか」という判断基準に照らして、改善すべき点
